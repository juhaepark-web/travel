# 여행지·숙소 사이트 기획 스킬

이 스킬은 여행지 소개 및 주변 숙소 예약 웹사이트를 기획할 때 사용한다.

## 진행 순서

1. 사용자가 제공한 기획, 기존 문서, 저장소 구조를 먼저 확인한다.
2. 기존에 정상 동작하는 기능이나 사용자가 정한 기술 규칙을 유지한다.
3. 핵심 이용자와 목적을 간단히 정리한다.
4. 공개 사용자, 로그인 회원, 관리자별 메뉴와 화면을 나눈다.
5. 각 화면의 파일명, 주요 내용, 주요 동작을 표로 정리한다.
6. 데이터 테이블은 기능에 필요한 최소 필드로 제안하고 기본키, 외래키, 필수 여부와 상태값을 표시한다.
7. 여행지 검색부터 숙소 예약과 예약 조회까지 사용자 흐름을 만든다.
8. 관리자 기능은 목록, 검색, 상세보기, 등록, 수정, 비활성화/삭제 흐름으로 설계한다.
9. 사용자가 정하지 않은 결제, 취소·환불 정책, 객실 재고, 숙소별 객실 구조, 개인정보 보관 정책은 사실처럼 단정하지 말고 결정 필요 항목으로 표시한다.
10. 구현 전에는 요구사항, 화면, 테이블, API 또는 데이터 저장 방식 사이의 누락과 충돌을 점검한다.

## 출력 기준

- 요약, 메뉴 구조, 화면 구조와 파일명, 데이터 테이블, 사용자 흐름, 관리자 대시보드, 미결정 항목 순으로 작성한다.
- 화면과 테이블은 표를 사용해 한눈에 비교할 수 있게 한다.
- 기능은 방문자, 회원, 관리자 권한을 구분한다.
- 예약의 가격과 상태는 예약 시점의 값이 보존되도록 설계한다.
- 회원 비밀번호를 평문으로 저장하거나 브라우저 코드에 비밀키를 넣는 설계를 제안하지 않는다.
- 실제 인증, 권한 검증, 개인정보 보호, 동시 예약 중복 방지는 신뢰할 수 있는 서버/API 또는 인증·데이터 서비스를 통해 처리해야 함을 명시한다.
- 브라우저 화면만 만들어 둔 경우 데이터가 실제 저장되거나 예약이 확정된 것처럼 표현하지 않는다.
- 사용자가 기존 파일을 제공했으면 새로 만들기 전에 관련 파일과 폴더를 분석한다.
- 한 번에 전체 기능을 구현하지 말고 사용자가 승인한 우선순위에 맞춰 작은 단계로 나눈다.

## 사용자의 기본 개발 규칙

기본 프런트엔드 기술은 HTML, CSS, 순수 JavaScript이다. TypeScript와 프런트엔드 프레임워크를 임의로 도입하지 않는다. CSS는 css 폴더, JavaScript는 js 폴더에 둔다. 페이지가 많으면 기능별 하위 폴더를 사용한다. 모든 주요 화면은 모바일에서도 사용할 수 있게 설계한다.

## 완료 전 점검

- 메뉴에서 필요한 모든 화면으로 이동할 수 있는가?
- 회원 전용 기능과 관리자 전용 기능이 구분되어 있는가?
- 예약에 필요한 회원, 숙소, 날짜, 인원, 금액, 상태가 연결되는가?
- 비활성화나 삭제가 기존 예약 기록을 훼손하지 않는가?
- 실제 결제와 예약 가능 객실 수가 미정이면 그 사실이 문서에 남아 있는가?
- 출력한 파일 경로와 실제 저장 위치가 서로 일치하는가?
